------------------------------------------------

MASTER ARCHITECTURE PRINCIPLE

We want one core platform engine that remains unchanged, while platform-specific behavior is controlled through configuration.

This means the following systems should remain reusable across all future platforms:

• Authentication system  
• Location detection and geocoding  
• Resource database schema  
• Resource approval workflow  
• CSV resource import tools  
• Saved resources / bookmarking  
• Lead routing engine  
• Escalation and navigator routing  
• Partner management  
• Admin dashboard  
• Usage logging  
• Rate limiting  
• AI engine framework  

These components should **never contain platform-specific wording or logic.**

All platform identity, terminology, and behavior should come from a central configuration file.

------------------------------------------------

The approach using:

shared/platform.ts

All branding, terminology, AI configuration, profile fields, and email behavior should be driven from that configuration.

------------------------------------------------

AI GUIDE ARCHITECTURE

The AI system should be built from the start as a reusable engine.

The server should contain a dedicated AI module:

server/ai/

engine.ts  
stream.ts  
prompt-builder.ts  
resource-matcher.ts  
rate-limiter.ts  
usage-logger.ts  
safety.ts  
config.ts

The first seven files should remain identical across platforms.

Only the configuration layer should change via the platform configuration file.

The AI prompt should be assembled using structured context:

1. System rules from platform.ai.systemRole  
2. User context (location, profile)  
3. Verified resources retrieved from the database  
4. The user’s question  

This ensures responses are grounded in actual resources and avoids hallucinations.

------------------------------------------------

DATABASE STRATEGY

The existing Supabase schema already supports a generic model.

Tables such as:

resources  
categories  
navigator_requests  
partner_organizations  
partner_routing_rules  
user_profiles  
user_saved_resources  
states  

are already platform-agnostic and should remain unchanged.

Each new platform should simply load a different dataset into the same schema.

------------------------------------------------

PLATFORM DUPLICATION STRATEGY

Future platforms should not require rewriting the application.

The process should be:

1. Duplicate the project repository
2. Edit shared/platform.ts
3. Load a new resource dataset
4. Replace branding assets
5. Connect a new Supabase project
6. Deploy

No core system logic should change.

------------------------------------------------

IMPORTANT ARCHITECTURE GUIDELINES

Please avoid introducing unnecessary complexity such as:

• Multi-tenant architecture with shared databases  
• Configurable Supabase schemas  
• Admin configuration editors for platform settings  
• Shared npm packages across platform instances  

Each platform should remain a **separate deployed instance** using the same architecture template.

This approach keeps systems isolated, reduces risk, and allows independent evolution of each platform.
